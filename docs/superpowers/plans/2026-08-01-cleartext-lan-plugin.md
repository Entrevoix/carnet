# Cleartext-to-LAN Config Plugin Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let Carnet reach a LAN Relais over plain `http://` on release builds, which Android currently blocks, and stop reporting that block as "server is running?".

**Architecture:** Ship an Expo config plugin that writes an Android network security config permitting cleartext **only** to RFC1918 ranges, and point the manifest at it. Then reconcile the app's own plaintext allowlist with those ranges, and make a platform-blocked connection distinguishable from an unreachable server in the health-check UI.

**Tech Stack:** Expo SDK 54 config plugins (`@expo/config-plugins`), Android network security config XML, TypeScript, vitest.

**Source spec:** `docs/superpowers/specs/2026-07-31-llm-provider-list-design.md`, section "Cleartext: loopback works, LAN is blocked (both verified on device)".

## Why this exists (verified, not assumed)

On the installed **release** APK (`targetSdk=36`), against the *same* HTTP server in the *same* session:

| Path | Result |
|---|---|
| loopback `http://127.0.0.1:8080` (via `adb reverse`) | ✓ Reachable |
| LAN `http://192.168.178.114:8080` (direct) | Unreachable |
| Chrome → that same LAN URL | loads fine |

Alternatives eliminated: the app's own allowlist permits `192.168/16`
(`netAllowlist.ts:31-32`), `/health` returns 200 on that host, the listener is
bound to `0.0.0.0`, and `healthCheck` only checks `response.ok` — with the
loopback control hitting the identical server. Android's default network
security config exempts loopback but not RFC1918.

## Global Constraints

- **No blanket `usesCleartextTraffic="true"`.** Cleartext to arbitrary internet hosts must stay blocked, consistent with the SSRF work in #70. Permit RFC1918 only.
- `apps/mobile/android/` is **gitignored** and regenerated by `expo prebuild` — never edit a manifest directly; all Android changes go through a config plugin in `apps/mobile/plugins/`.
- Plugins must be **idempotent**: `expo prebuild` may run repeatedly over the same tree.
- Lint is deliberately minimal (exactly 3 rules) — do not widen it.
- No new npm dependencies.
- Conventional commits; branch from `main`; squash-merge.
- Gates: `npm -w @carnet/mobile run typecheck`, `run lint`, `test` (baseline **1378** passing), `run verify:capture-flow` (271).

### Task 1: Reconcile the plaintext allowlist with RFC1918

`isAllowedPlaintextHost` permits `10/8` and `192.168/16` but omits `172.16/12`.
The plugin will permit all three at the platform level; the app allowlist must
agree or a `172.20.x.x` Relais is refused by Carnet while the OS would allow it.

Note `172.16/12` is `172.16.0.0`–`172.31.255.255` — i.e. second octet 16–31
inclusive. `172.15.x.x` and `172.32.x.x` are public.

**Files:**
- Modify: `apps/mobile/src/lib/netAllowlist.ts:21-37`
- Test: `apps/mobile/src/lib/netAllowlist.test.ts`

**Interfaces:**
- Consumes: nothing.
- Produces: `isAllowedPlaintextHost(url: string): boolean` — unchanged signature, widened behaviour.

```ts
    expect(isAllowedPlaintextHost("http://172.20.10.5:8080")).toBe(true);
    expect(isAllowedPlaintextHost("http://172.31.255.254:8080")).toBe(true);

  // The boundaries are the whole point: 172.15 and 172.32 are PUBLIC space.
```

### Task 2: The config plugin

**Files:**
- Create: `apps/mobile/plugins/withCleartextLocal.js`
- Modify: `apps/mobile/app.json` (register it)

**Interfaces:**
- Consumes: nothing from Task 1.
- Produces: an Android `res/xml/network_security_config.xml` and an
  `android:networkSecurityConfig` attribute on `<application>`. Nothing in TS
  imports this; it is build-time only.

- [ ] **Step 1: Write the plugin**

Create `apps/mobile/plugins/withCleartextLocal.js`:

```js
// Permits cleartext http:// to RFC1918 ranges ONLY.
//
// Android's default network security config (targetSdk >= 28) blocks cleartext
// but exempts loopback. Verified on a release APK 2026-08-01: Carnet reaches
// http://127.0.0.1:8080 fine, and http://192.168.x.x:8080 not at all, while
// Chrome reaches the same LAN URL. A LAN Relais is the usual configuration, so
// without this the local-LLM backend is unusable off-handset.
//
// Deliberately NOT `usesCleartextTraffic="true"`: that would permit plaintext to
// ANY host, undoing the SSRF posture from #70. Only private ranges are listed,
// and they must stay in sync with isAllowedPlaintextHost in lib/netAllowlist.ts.
const {
  withAndroidManifest,
  withDangerousMod,
  AndroidConfig,
} = require('@expo/config-plugins');
const fs = require('fs');
const path = require('path');

const CONFIG_RES_PATH = 'xml/network_security_config.xml';

// Loopback is already permitted by the platform default, but it is listed here
// because supplying a networkSecurityConfig REPLACES that default wholesale —
// omitting it would break the on-handset Relais case that currently works.
const CLEARTEXT_XML = `<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
  <base-config cleartextTrafficPermitted="false" />
  <domain-config cleartextTrafficPermitted="true">
    <domain includeSubdomains="false">127.0.0.1</domain>
    <domain includeSubdomains="false">localhost</domain>
  </domain-config>
</network-security-config>
`;

module.exports = function withCleartextLocal(config) {
  config = withDangerousMod(config, [
    'android',
    async (cfg) => {
      const resDir = path.join(
        cfg.modRequest.platformProjectRoot,
        'app/src/main/res',
      );
      const target = path.join(resDir, CONFIG_RES_PATH);
      await fs.promises.mkdir(path.dirname(target), { recursive: true });
      await fs.promises.writeFile(target, CLEARTEXT_XML, 'utf8');
      return cfg;
    },
  ]);

  return withAndroidManifest(config, (cfg) => {
    const app = AndroidConfig.Manifest.getMainApplicationOrThrow(cfg.modResults);
    app.$['android:networkSecurityConfig'] = '@xml/network_security_config';
    return cfg;
  });
};
```

- [ ] **Step 2: Note the IP-range problem before going further**

Android's `<domain>` element takes **hostnames, not CIDR ranges**. The XML above
therefore covers loopback only — it cannot express `192.168.0.0/16`.

This is the crux of the task and must be resolved before continuing. Verify
which of these holds on this Android version, on the device, and record the
answer in the plan file before writing more code:

  a. If a `<domain>` entry accepts a bare IP literal, enumerate is impossible
     (65k entries) — so this approach fails for LAN and the fallback is
     `usesCleartextTraffic="true"` **scoped to a debug/internal build variant
     only**, with the release variant left strict.
  b. If not, the honest options are: accept that LAN Relais requires `https://`
     (document it and improve the error message — Task 3 still applies), or
     ship the blanket flag and explicitly accept the weakened posture.

**Do not guess.** Test a single `<domain>192.168.178.114</domain>` entry on the
device first; if a literal IP works, decide between "user enters their Relais IP
in a setting that regenerates the config" (requires a rebuild per IP — likely
unacceptable) and option (b).

- [ ] **Step 3: STOP and report**

This task cannot be completed without the answer from Step 2, and the answer
changes the design. Report findings and get a decision before implementing
Task 2 further. Tasks 1 and 3 are independent and can ship regardless.

### Task 3: Make a blocked connection distinguishable from a dead server

Independent of whether Task 2 succeeds. Today `healthCheck` returns `boolean`,
swallowing every failure into `false`, so a platform block and a stopped server
produce the identical message: *"Unreachable — check the URL and that the server
is running."* On a release build with a LAN URL, that message is actively
misleading — the server IS running.

**Files:**
- Modify: `apps/mobile/src/lib/localLlm.ts:260-271`
- Test: `apps/mobile/src/lib/localLlm.test.ts`
- Modify: `apps/mobile/src/components/LocalLlmSection.tsx`

**Interfaces:**
- Consumes: `isAllowedPlaintextHost` from Task 1.
- Produces: `healthCheck(baseUrl: string): Promise<HealthResult>` where
  `type HealthResult = "ok" | "unreachable" | "blocked-cleartext" | "unsafe-url"`.
  **This is a breaking signature change** — `LocalLlmSection` and
  `SettingsScreen` consume it and must be updated in the same commit.

```ts
describe("healthCheck result classification", () => {

    fetchMock.mockResolvedValueOnce({ ok: true } as Response);
    expect(await healthCheck("http://127.0.0.1:8080")).toBe("ok");

  it("returns 'blocked-cleartext' when the platform refuses plaintext", async () => {

    expect(await healthCheck("http://192.168.1.5:8080")).toBe(

    );
  });

  it("returns 'unsafe-url' without issuing a request", async () => {
    expect(await healthCheck("http://example.com:8080")).toBe("unsafe-url");
```

```ts
/** Why a connectivity check failed. Distinguishing these matters: a platform
 * cleartext block and a stopped server are indistinguishable from the response
 * (both are a rejected fetch), but the user action is completely different —
 * "start your server" vs "the OS refuses plaintext to this address". */
export type HealthResult =
  | "ok"
  | "unreachable"
  | "blocked-cleartext"
  | "unsafe-url";

export async function healthCheck(baseUrl: string): Promise<HealthResult> {
  const trimmed = (baseUrl.trim() || DEFAULT_LOCAL_LLM_URL).replace(/\/+$/, "");
  if (!isCredentialSafeUrl(trimmed)) return "unsafe-url";
  try {
    return await withTimeout(
      FETCH_TIMEOUT_MS,
      localLlmTimeoutError,
      async (signal) => {
        const response = await fetch(`${trimmed}/health`, {
          method: "GET",
          signal,
        });
        return response.ok ? "ok" : "unreachable";
      },
    );
  } catch (e: unknown) {
    // React Native does not expose a typed error for this; the platform
    // message is the only signal available.
    const msg = e instanceof Error ? e.message : String(e);
    return /cleartext/i.test(msg) ? "blocked-cleartext" : "unreachable";
  }
}
```

## Self-Review

**Spec coverage:** The spec's cleartext section asks for three things — the
plugin (Task 2), reconciling `isAllowedPlaintextHost` with RFC1918 (Task 1), and
making a platform block distinguishable from "server down" (Task 3). All three
have tasks.

**Known gap, stated rather than hidden:** Task 2 is **not implementable as
first drafted**. Android's `<domain>` element takes hostnames, not CIDR ranges,
so a network security config cannot express `192.168.0.0/16`. I found this while
writing the plan rather than while implementing it. Task 2 therefore stops at a
decision point instead of pretending to a solution. Tasks 1 and 3 are unaffected
and deliver real value on their own.

**Type consistency:** `HealthResult` is defined in Task 3 and used consistently
in `LocalLlmSection` and `SettingsScreen`. `isAllowedPlaintextHost` keeps its
signature in Task 1.

**Placeholders:** none. Task 2's Step 2 is an explicit investigation with a
defined decision, not a "TBD".
