## The stale-prebuild trap (read this before the next release)

`apps/mobile/scripts/build-release-apk.sh` only **checks that** `android/` exists — it never
regenerates it. After #136 merged, `android/app/build.gradle` still read
`versionCode 1 / versionName "0.2.0"` from an older prebuild. Building without
regenerating would have produced an APK named `carnet-v0.4.0.apk` that
self-reported `0.2.0` — reintroducing the exact drift #136 existed to remove,
silently and with every test green.

**After any version change, all of these from `apps/mobile`:**
1. `export ANDROID_HOME="$HOME/Android/Sdk"` — `prebuild --clean` wipes
   `local.properties`, so a local Gradle run without this fails with "SDK
   location not found" (learned in the 2026-08-06 handoff; do not learn it a
   third time).
2. `npx expo prebuild --platform android --clean`
3. `grep -nE "versionCode|versionName" android/app/build.gradle` — confirm it
   reflects the bump.
4. Re-run `scripts/verify-notification-and-widget-prebuild.sh`,
   `verify-audio-decoder-prebuild.sh` and `verify-shortcuts-prebuild.sh` — a
   `--clean` regeneration is exactly when the config plugins can silently stop
   emitting what they should.
5. After building, verify the APK's cert before trusting it as a release:
   `apksigner verify --print-certs <apk>` must print
   `e5f5ed37e098e0da7b09a59734845b21c986a18d1994bbdb670d01e3c7a3eaf7`.
   `build-release-apk.sh` **falls back to the debug keystore and still exits 0**
   if the keystore config is missing — `release.yml` treats this exact
   fall-through as mandatory to check, and a debug-signed APK cannot upgrade a
   release-signed install without an uninstall that wipes all app data.

CI is immune — the
`android-toolchain` composite action does a clean prebuild every run. This bites
local builds only, which is precisely where releases get hand-checked.

**Read back 2026-08-08.** The note was **completely unchanged** — H1 still

Re-running it on-device surfaced the actual outcome:

> ⚠ **Enhance failed: OmniRoute unreachable — timed out after 120s. Check your
> connection (Tailscale?).**

**Root cause: the LLM gateway is offline.** `llm.grepon.cc` resolves to the
tailnet address `fd7a:115c:a1e0::be33:ce0f`, and `ping6` **from comet itself**
(Tailscale connected to `beary.us`) returns 100% packet loss. Nothing app-side is
broken. Note the gateway was up on 2026-08-06 — the test capture enriched fine at
18:57 — so it went down between then and 2026-08-08. Do not debug this in the app.

**What that verifies (new, and worth having):** the Enhance *failure* path now has
real device evidence. The 120s timeout fires, the error names the service, the
elapsed time and the likely cause, and **the note is left byte-untouched — no
partial write, no lost title, no data loss.** That is the guard doing its job
against a dead backend, which no unit test can prove.

Do not diagnose this as a missing timeout: `llmClient.ts:177` sets
`ENHANCE_TIMEOUT_MS = 120_000`, deliberately distinct from the 20s
`FETCH_TIMEOUT_MS` used elsewhere, because Enhance reaches for a slower model.
A spinner still running at 60s is inside spec, not a hang.

**Still unverified — needs the gateway back up:** the happy path. Specifically
that a *successful* rewrite preserves the H1 (#133) and the URL, and actually
improves the prose:

- H1 must still read **`v0.4.0 Enhance Action Smoke Test`** (#133, title loss)
- body must still contain **`https://example.com/carnet-smoke`** (URL backstop)
- prose itself should be rewritten

Note that the *logic* here is already pinned by `enhanceProse.test.ts` —
including `keeps the title on an Obsidian-style note`, `replaces the prose while
preserving frontmatter and title byte-for-byte`, and the four mid-flight guard
cases (`prefers the file's CURRENT content over the caller's stale snapshot`,
`captures the mtime baseline BEFORE the model call, not after`, `keeps the
user's version when the note changed mid-flight`, `passes the captured baseline
through to the guarded write`). Note the byte-for-byte test asserts `toContain`
on the frontmatter fields and H1, not literal byte equality — its name
overclaims slightly. The device run adds real
model output through Hermes onto a real vault file, not logical coverage.

**Keep the test note on comet** ("v0.4.0 Enhance Action Smoke Test", Idea,
`#testing #development #v040`). It is the fixture for the happy-path run — it
carries a URL specifically to exercise the backstop. Delete it only after a

## Rig notes (cost real time this session)

- **comet's USB is unreliable — it dropped three separate times across this
  work.** `adb reconnect` / `adb reconnect offline` / a server restart never
  recover it; it needs a physical replug. rango dropped once too. Assume any long
  device sequence on comet will be cut off partway: take the readback you need
  early, and never leave the only evidence of a result sitting unread on the
  phone.
- **`uiautomator dump` cannot detect a spinner.** It waits for the window to go
  idle, and an indeterminate progress indicator never goes idle — so the dump
  fails, any grep against it returns nothing, and a poll loop reads that as "the
  spinner cleared." It silently reports the opposite of the truth. Poll with
  `screencap` instead, which has no idle requirement. (Cost real time here: a
  loop concluded an Enhance run had finished when it was still 60s from its
  timeout.)
- **rango has no LLM provider configured** — Base URL, API key, and Model are all
  empty. It cannot stand in for Enhance testing without entering credentials, and
  the key cannot be copied off comet (secure store, never displayed again).
  Separately, rango's Recents is empty; **that is not caused by the missing
  provider** — `docs/smoke-test.md` §"Capture — Person (without the gateway)"
  documents captures landing on disk with no provider at all. Cause undiagnosed;
  check the configured capture folder first.
- **`screencap` on a Fold emits a multi-display warning strip before the PNG**,
  corrupting the file. Strip to the `\x89PNG` magic, or pass a real `-d
  <display-id>` — **`-d 0` is not a valid display id here** (they look like
  `4619827677550801152`); `dumpsys SurfaceFlinger --display-id` lists them.
- **For taps, follow the focus-assert procedure in the 2026-08-06 handoff — NOT
  `input -d 0`.** This session tapped blind with `input -d 0` throughout and
  every tap happened to land on Carnet, so nothing went wrong. That is luck, not
  a correction of that handoff: the previous session recorded `input -d 0 tap`
  misrouting into **Google Authenticator's export screen**, which is why the
  `dumpsys window | grep mCurrentFocus` guard before every tap exists. `-d 0`
  appearing to work is not evidence that it is safe, and this session skipped
  the guard rather than disproving the need for it.
